# Payment due-date calculator

Route `/tools/payment-due-date`, navigation “Payment due-date calculator”. Select a company from the existing authorized entity list. Enter invoice date, choose Net0/7/14/30/45/60/90 or Custom0..365, and review/edit the visible as-of date (defaults to the browser's local calendar date). Calculate shows due date, due-in/today/overdue status, absolute day count and the submitted as-of date. Terms use calendar days without weekend/holiday adjustment. The tool does not check payment or legal obligations. Overdue results explicitly say payment status was not checked.

Uses the shared SessionGate, authorized entity loader and typed API transport. No fixtures, business-record/history writes, browser storage, new dependencies or migration. Read-only company permission is enough. Any input/company change and Reset abort the request and clear its result; generation checks ignore late responses. Leaving/sign-out unmounts the form and discards results. Only a 200 response with strict schema, real dates, matching inputs/entity, correct calendar arithmetic and matching status/day sign may be displayed.

For the prepared local environment: backend `npm run build && npm start`; frontend `VITE_API_BASE_URL=http://127.0.0.1:3000/api/v1 npm run dev -- --host 127.0.0.1 --port 5173 --strictPort`. Existing installations keep their normal database/session configuration. Fresh installations follow backend/README.md; no calculator migration/seed is needed. For a future authorized deployment, use existing VITE_AUTH_MODE=session and same-origin /api/v1 proxy settings; no new host/secret changes are part of this task.

Manual journey: open the route → select authorized company → invoice2026-10-01, Net30, as-of2026-11-02 → Calculate → due2026-10-31, two days overdue → change any input to clear the result → Reset to blank invoice/Net30/local today. Try Net0 on the invoice date for Due today. Disconnect the API to check visible failure without a result. Read-only accounts can calculate; inaccessible companies cannot. Existing financial demo state must remain unchanged.

Checks: `npm run typecheck`, `npm run lint`, `npm run build`, `npm run test:payment-due-date`; the dedicated browser suite reuses the existing isolated synthetic PostgreSQL/entity fixture and actual child API. `npm run test:session` exercises calculator sign-in/proxy/CSRF and discarding on sign-out.
