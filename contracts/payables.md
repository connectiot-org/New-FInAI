# Payables pilot contract 1.0.0

Additive, session-authorized `/api/v1/payables`. Existing error/request-ID and CSRF/host rules apply. Identity never comes from payloads. All UUID operations scoped by organisation/entity. Explicit AP grants view/review/verify/approve/manage; organisation administrators may provision others' grants, never themselves. Entity access and active membership remain necessary. Reads use safe404; insufficient action403. No implicit administrator approval.

Money: GBP only; quantity decimal strings (4 places), unit price integer minor-unit strings; tax basis points 0 or2000, explicit tax code NONE or STANDARD, recoverability boolean. One tax treatment per invoice; mixed treatments remain blocked. Half-up rounding per line using BigInt. Total bounds £10m per invoice, maximum50 lines. Declared gross retained separately; mismatch or missing coding blocks review. Account codes and cost centre explicitly entered/confirmed for the synthetic pilot, not production tax certification.

Invoice has version (every mutation), revision (material metadata/document edit), approval state review/verify/approve/approved/rejected; independent validation and export state; payment always unpaid. Patch creates a new revision and clears routing; rejection cannot be reopened. Review freezes published policy, selected first-match amount rule or mandatory fallback, verifier and 1–2 sequential approvers; submitter cannot approve. Challenge/reject require reasons. Policy edits never mutate frozen routes. Decisions are retry-safe with operation UUID and digest and bind version/revision. Export is immutable once per approved revision; a new operation UUID replays same logical export. Prior exports become superseded after material edits.

All JSON objects strict; errors422. Version mismatch409. Same operation UUID/identical canonical body replays; different body409. Duplicate supplier/reference normalized NFKC/trim/lowercase in entity and bill type returns409; correction requires explicit metadata change, not fuzzy discard. Supplier versions independent.

Routes:
- GET capabilities?entityId: grants plus eligible member choices.
- GET/POST suppliers; PATCH suppliers/:id. POST {id,entityId,name,taxId}; PATCH {expectedVersion,name,taxId,active}.
- GET invoices?entityId,queue=all|review|verify|approve|export,search,status,dueBefore,assignee,offset,limit (default20, maximum50), ordered createdAt/id descending. Counts use same search/status/date/person filters across complete authorized result set, independent of page and queue.
- POST invoices {id,entityId,supplierId,reference,invoiceDate,dueDate,currency,declaredGross,lines}; PATCH invoices/:id {expectedVersion,...same metadata except id/entityId}. GET invoices/:id returns metadata, source documents (without bytes), history, frozen route and calculated totals.
- POST invoices/:id/documents?entityId&operationId&expectedVersion&filename: application/pdf, max1MiB. Session/CSRF/review grant before buffering; no compression. Signature/EOF checks; immutable bytea. Real files require a clean result from the configured trusted scanner; otherwise they remain quarantined or infected. Only an exact allowlisted test fixture under NODE_ENV=test may be marked synthetic, visibly distinct from clean/scanned. Quarantined documents cannot preview or satisfy review. A healthy target scanner with fresh signatures is an operational release gate.
- GET invoices/:id/documents/:documentId: private application/pdf attachment; sandbox/no-store/nosniff; safe generated filename.
- POST invoices/:id/actions {operationId,expectedVersion,action=review|verify|approve|correction|challenge|reject,reason?}. Current assignment/capability checked atomically, routing and safe audit saved with event.
- GET approval-policies?entityId; POST approval-policies {operationId,entityId,expectedVersion,publish,definition}. Definition {currency:GBP,rules:[{priority,minimumGross,verifierId,approverIds}],fallback:{verifierId,approverIds}}. Draft/save and publish distinct. Assignees must have corresponding grants and active entity membership. Currency fixed; thresholds distinct and descending; bounded10 rules; no auto approval. GET result separates draft and published.
- POST grants {entityId,userId,view,review,verify,approve,manage}: existing organisation administrator only, cannot target self; target must have entity access. Changes revoke the affected member’s organisation sessions. No browser identity selectors.
- POST invoices/:id/exports {operationId,expectedVersion}: review capability, approved current revision. Balanced CSV expense/tax debits and supplier payable credit with mapping and revision. GET exports/:id/file: immutable private text/csv attachment, not posting evidence.

Source of truth for strict executable payload schemas: backend/src/payables/domain.ts; public companion schemas/examples are validated by contracts/validate_payables.mjs. No existing workspace context schema changes.

All POST endpoints currently return201 for both a new result and an identical authorized replay. The scoped private client validates response schemas and checks the current identity epoch before sending a mutation and after reading its response.

Administrator tooling: GET `/grants?entityId` lists existing entity members with their explicit AP capabilities. This endpoint requires active organisation administration and never grants financial access implicitly. The private `/workspace/payables/settings/access` screen permits deliberate changes for other members; self-provisioning remains refused.

Document scanning: trusted `AP_CLAMD_HOST`/`AP_CLAMD_PORT` configure a private ClamAV INSTREAM endpoint. Scans require identifiable signatures no older than seven days. Clean files may preview/review; infected, stale-signature, unavailable or inconclusive scans remain blocked. POST `/invoices/:id/documents/:documentId/scan` takes `{operationId,expectedVersion}`, preserves original bytes, records the verdict, and creates a new review revision. Scan provenance is exposed in document metadata. No browser-supplied verdict or scanner address is accepted.

Review correction requests: action `correction` requires review permission, current review state, and a reason. It records an unresolved finding without sending an email. Detail exposes `correctionReason`; submission is blocked until a reviewer saves corrected metadata. That save creates a new revision and clears the finding. The attention indicator includes unresolved correction requests.

## Additive contract 1.1.0

The optional `month=YYYY-MM` invoice-list filter selects invoice issue dates and combines with existing search/queue filters. Assistant source links retain exact company, month and literal supplier/reference search. Existing clients omitting the filter retain their previous results. The session-only `/invoices/{id}/assistant-actions` command and optional Assistant proposal fields are defined in [invoice-assistant.md](invoice-assistant.md). Financial rules and prior endpoints retain their meanings; no new migration is required.
